# Brise 클라이언트 규칙 (SSOT)

목적: 데스크톱 Brise 외의 "위성" 클라이언트(모바일 웹 뷰어, 그리고 이후 나올 수 있는 다른 앱)가
반드시 지켜야 할 계약을 한 곳에 못박는다. 첫 사례는 **Tailscale tailnet 경유 모바일 읽기 전용
웹 뷰어**다.
작성: 2026-07-29. 관련 문서: `docs/SYNC.md`(동기화 전략 SSOT), `docs/SCALABILITY.md`(성능 예산).

이 문서와 `docs/SYNC.md` 의 관계: SYNC.md 는 "언제·왜 무엇을 만드나"(로드맵, 옵션 비교),
이 문서는 "일단 클라이언트가 하나라도 생기면 절대 어겨선 안 되는 계약"이다. 후자가 전자보다
오래 산다 — 동기화 옵션이 바뀌어도(옵션 2 → 옵션 5 등) 클라이언트 계약의 하위호환·보안·버전
협상 규칙은 그대로 유지되어야 한다.

각 규칙 항목은 **규칙**(normative — 어겨선 안 됨) 또는 **현재 구현**(informative — 오늘 시점의
실제 코드 상태, 서버가 아직 개발 중이라 바뀔 수 있음)으로 표시한다.

---

## 1. 적용 대상과 목적

- 데스크톱 Brise(Tauri 앱, SQLite 파일 원본 소유)가 **원본(source of truth)** 이다.
- 그 외 모든 클라이언트 — 모바일 웹 뷰어, 향후 나올 다른 앱(네이티브 모바일, 다른 데스크톱
  인스턴스 등) — 는 **위성**이다. 위성은 원본을 읽거나(read), 미래에는 원본에 기여(write)할 수
  있지만, 원본이 될 수 없다.
- 첫 위성: 데스크톱 앱이 내장 HTTP 서버를 켜고, 같은 tailnet 위의 휴대폰 브라우저가 접속해
  노트를 **읽기 전용**으로 보는 모바일 웹 페이지.
- 이 문서는 그 첫 사례뿐 아니라 **앞으로 추가되는 모든 클라이언트**에 적용된다 — 특정 클라이언트
  하나를 위한 예외를 만들지 않는다(장기 안정성 우선).

## 2. 데이터 접근 규칙

**규칙**
1. 어떤 클라이언트도 `brise.db`(SQLite 파일)에 직접 접근할 수 없다 — 파일 공유 폴더, 네트워크
   드라이브, 원격 파일시스템 마운트 어느 경로로도 금지. `docs/SYNC.md` §6 공통 원칙("SQLite
   파일 자체를 네트워크/동기화 폴더에 노출하지 않는다")과 동일한 이유: `-wal` 부분 읽기는 손상된
   상태를 관측할 수 있고, 쓰기는 동시성 보장이 전혀 없다.
2. 유일한 접근 경로는 **버전드 HTTP API**(`/api/v1/...`)다. 클라이언트는 이 API의 응답 형태만
   신뢰한다 — 테이블 이름, 컬럼 이름, SQL 스키마는 클라이언트 입장에서 존재하지 않는 것으로
   취급한다.
3. `/api/v1` 하위호환 규칙(엄격):
   - 기존 응답 필드는 **제거 금지**, **의미 변경 금지**(타입을 바꾸거나 단위를 바꾸는 것도
     의미 변경이다).
   - 새 필드는 **항상 optional**로 추가한다 — 구버전 클라이언트가 필드를 몰라도 파싱이 깨지면
     안 된다.
   - 파괴적 변경(필드 제거·의미 변경·필수화)이 필요하면 `/api/v2`를 새로 만든다. `/api/v1`은
     `/api/v2`가 나온 뒤에도 기존 클라이언트가 남아있는 한 계속 응답해야 한다.
4. 서버(데스크톱 앱의 HTTP 레이어)는 API 응답을 만들 때 항상 repo 계층(`src-tauri/src/repo/*`)을
   경유한다 — DB 쿼리를 API 핸들러에 직접 박아 넣지 않는다. `docs/SYNC.md` §6 "모든 동기화
   쓰기는 repo 계층 단일 경로 경유"와 동일한 원칙을 읽기에도 적용한다(스키마 변경 시 갱신 지점을
   하나로 유지).
5. **`POST /api/v1/invoke`(커맨드 브리지) — 1st-party 웹 클라이언트 전용.** `{"cmd": "<name>",
   "args": {...}}` → 그 Tauri 커맨드가 네이티브 `invoke()`로 반환했을 그 JSON을 그대로 반환한다.
   대상 커맨드 집합은 `specs/commands/*.yaml`의 `http` 플래그(생략 시 기본 `true`)가 SSOT이고,
   `scripts/gen-commands.mjs`가 그로부터 `src-tauri/src/sync_server/dispatch.gen.rs`를 생성한다
   (수동 편집 금지 — commands.gen.ts와 동일한 계약). `http:false`로 표시된 커맨드는 이 엔드포인트로
   **영원히** 도달 불가능하다 — 다음은 구현 세부사항이 아니라 **영구 규칙**이다:
   - **OS UI/다이얼로그**를 여는 커맨드 (예: `attachment_open`, `attachment_reveal`,
     `data_dir_open`) — 원격 클라이언트는 서버 머신의 OS를 조작할 수 없다.
   - **로컬 파일시스템 경로**를 인자로 받는 커맨드 (`file_path`/`dest_path`/`dest_dir`/
     `source_dir`/`zip_path`/`bundle_path`/`enex_path` 등 — 데스크톱 파일 다이얼로그가 고른 경로는
     원격 클라이언트 입장에서 애초에 존재하지 않는 경로다).
   - **파괴적이거나 서버 머신 로컬 상태에 부수효과가 있는 관리 동작** (`db_reset`,
     `backup_restore`, `backup_auto_run`, 마이그레이션 임포트 등).
   - **네이티브 하드웨어**를 잡는 커맨드 (`dictation_*` — 서버 머신의 실물 마이크).
   - **서버 자신의 lifecycle을 제어하는 커맨드** (`sync_set_enabled`, `sync_regenerate_token`,
     `sync_status`) — 원격 클라이언트가 자신이 접속한 서버를 끄거나 토큰을 재발급할 수 없어야
     한다. `settings_set`이 이 규칙을 우회하는 뒷문이 되지 않도록, `sync_*`로 시작하는 설정 키는
     `settings_set` 호출 자체에서도 별도로 차단한다(서버 lifecycle 예외 클래스의 일부 —
     `src-tauri/src/sync_server/handlers.rs::invoke`).
   **개방 결정(오너, 2026-10-06 — 개인 앱):** 사이드바 AI 채팅 코어(`pet_chat` ·
   `pet_chat_history` · `pet_chat_clear` · `pet_session_list/new/open` · `pet_chat_rewind` ·
   `pet_chat_delete` · `pet_note_create` · `pet_conversation_save`)는
   `http: true` 다 — 폰/웹(`/app`)이 PC 의 sync_server(Tailscale + 토큰) 경유로 채팅을 쓴다. 이전
   "pet_chat 은 레이트리밋 밖 로컬 경로" 전제(`docs/PLAN-2026-08-04-dashboard-pet.md` §P)는 폐기:
   개인 앱이므로 별도 레이트리밋은 두지 않고, 대신 **실패 가시성**을 규칙으로 한다 — 프로바이더
   오류·429·타임아웃·프라이버시 게이트 거부는 진단 싱크에 남고(Rust `diag::warn("pet","chat_failed")`,
   프런트 `call()` → `logError`) 폰 사용자에게 사유와 함께 보인다. **여전히 `http: false`**: 펫 창·
   말풍선·에셋/패키지·스크린샷·테마·위치·가시성·알림·`pet_open_main`/`pet_close`(서버 머신 창/OS
   조작) 및 `pet_chat_read_attach`(서버 **로컬 경로**를 읽는다 — 원격이면 임의 파일 읽기이므로 위
   "로컬 파일시스템 경로" 규칙 그대로. 브라우저 첨부는 File→base64 를 클라이언트에서 한다).
   `pet-chat-updated` 는 `AppHandle` 파라미터 없이 `crate::events::publish_event` 로 내보낸다
   (데스크톱 웹뷰 + SSE 프레임 `pet-chat-updated`).
   에러 응답은 `{"error": "<string>"}` 셰이프(unknown cmd → 404, args 역직렬화 실패 → 400,
   커맨드의 `AppError` → CONFLICT 는 409, 그 밖은 500). 커맨드 자체의 에러에는 **additive
   `"code"`**(네이티브와 같은 `AppError` 코드, 2026-10-07~)가 붙는다 — 클라이언트는 상태보다
   `code` 를 먼저 본다. 도메인 NOT_FOUND 는 404 가 아니다(404 = HTTP 표면 밖 커맨드). 다른
   `/api/v1/*` 엔드포인트의 NotFound→404/Validation→400 매핑과는 다르다.
6. **`GET /api/v1/events`(SSE)** — 토큰은 쿼리 파라미터로만(`EventSource`는 커스텀 헤더를 못
   보낸다). v1은 `remote-note-write` 이벤트만 실어 나른다(다른 기기의 쓰기를 웹 클라이언트가
   재조회 트리거로 쓰는 용도).

**현재 구현**
- 서버 엔드포인트: `GET /api/v1/ping`, `GET /api/v1/notes`(목록),
  `POST /api/v1/notes/:id/checklist`, `POST /api/v1/notes/:id/attachments`(업로드),
  `GET /api/v1/attachments/:note_id/*`(첨부 서빙), `POST /api/v1/invoke`,
  `GET /api/v1/events`(SSE), 웹 클라이언트 정적 서빙 `/app`(`/app/*`, 인증 없음 — 정적 번들
  자체는 비밀이 아니고 실제 데이터 호출만 `/api/v1/*`에서 토큰을 요구한다). `/m`과 루트 `/`는
  구형 모바일 뷰어 셸이 있던 자리로 이제 쿼리스트링(토큰 포함)을 보존한 채 `/app`으로 307
  리다이렉트만 한다. `POST /api/v1/notes` · `PUT /api/v1/notes/{id}` · `GET /api/v1/notes/{id}`
  REST CRUD와 `/api/v1/snapshot`은 없다 — 노트 생성/수정/단건 조회는 `POST /api/v1/invoke`.
  정확한 응답 스키마는 서버 구현(`src-tauri/src/sync_server/handlers.rs`)을 SSOT로 본다 —
  이 문서는 필드 목록이 아니라 위 하위호환 규칙을 강제한다.

## 3. 버전 협상

**규칙**
1. 클라이언트는 접속 시 `ping` 엔드포인트로 (a) 앱 버전, (b) DB 스키마 버전
   (`schema_migrations` 최신 버전, `migrations::current_version`과 동일한 값)을 확인한다.
2. 클라이언트가 **모르는 스키마 메이저 변화**(클라이언트가 마지막으로 알던 버전보다 서버 스키마
   버전이 높음)를 감지하면, 읽기 전용 기능이라도 **보수적으로 축소**한다 — 모르는 필드가 뷰를
   깨뜨릴 수 있는 화면은 숨기거나 "앱을 업데이트하세요" 안내로 대체한다. 무조건 렌더를 시도해
   깨진 상태를 보여주지 않는다.
3. 번들(export bundle)·스냅샷(백업 zip, 향후 동기화 스냅샷)의 스키마 버전 비교:
   - **자기(수신 측)보다 높은 schema version의 번들·스냅샷은 거부한다** — 명확한 에러로,
     조용히 일부만 받아들이지 않는다.
   - **낮은 버전은 수용한다**(구버전 데이터를 최신 스키마로 마이그레이션해서 받는 것은 안전).
   - 이 규칙은 이미 데스크톱 앱 자체 안에서 구현되어 있다 — 아래 "현재 구현" 참고. 새로 생기는
     모든 전송 경로(서버 snapshot 엔드포인트 포함)는 동일한 비교 방향을 따라야 한다.

**현재 구현**
- `repo/transfer/import.rs::import_bundle`: `bundle.version > cur` 이면
  `"bundle version {bundle.version} newer than schema {cur}"` 로 거부, 낮은 버전은 통과시켜
  기존 `insert_*` 경로로 최신 스키마에 맞춰 삽입한다.
- `repo/transfer/backup.rs::stage_from_zip`: `backup_schema < 1 || backup_schema > cur_schema`
  면 거부(0은 `schema_migrations` 자체가 없는 비-Brise 파일, 상한 초과는 미래 스키마). 하한 위반과
  상한 위반을 한 조건에 묶은 이유는 코드 주석 참고 — 이 문서에서 중요한 건 "높은 쪽은 항상 거부"
  방향성이다.
- ping 엔드포인트의 정확한 응답 필드는 서버 구현(동시 진행) 확정 시 이 절에 반영한다.

## 4. 쓰기 규칙 (미래 대비)

**규칙**

수정(2026-07-30): 아래 문단은 원래 "첫 클라이언트는 읽기 전용이라 이 절은 당장 적용 대상이
없다"고 적혀 있었으나, 그 사이 쓰기 엔드포인트(노트 생성/수정, 체크리스트 토글, 첨부 업로드)가
이미 배포됐다 — §8("코드가 이 문서의 규칙과 어긋나면 코드가 버그")에 따라 사실과 다른 전제를
그대로 두지 않는다. **실제 배포된 계약은 "단일 소유자 쓰기 베타"**다: 소유자 본인이 자신의
데스크톱과 자신의 휴대폰 사이에서만 쓴다고 전제하고, 두 기기가 정말로 동시에 같은 노트를 쓰는
상황에 대한 동시성 보장은 아직 없다(아래 4.1~4.3은 이미 구현됐고, 4.4~4.6은 그 상황이 실제로
닥치기 전까지는 괜찮은 채로 남아있는 추적 부채 — "현재 구현" 항목 참고). 양방향 동기화
(`docs/SYNC.md` Phase 2, 여러 기기가 정말 동시에 쓸 수 있는 상태)로 넘어가기 전까지 예외 없이
강제되어야 하는 것은 여전히 아래 규칙 전부다.

1. **LWW(last-write-wins)** 를 따른다. 충돌 시 `updated_at` 이 더 최신인 쪽이 승리한다.
2. `updated_at` 은 **UTC, 밀리초 정밀도**로 기록한다. 데스크톱 DB의 모든 실쓰기 경로가 공유하는
   `util::now_iso()` 가 이미 `chrono::Utc::now().to_rfc3339_opts(SecondsFormat::Millis, true)`
   로 밀리초 정밀도 ISO8601 UTC 텍스트를 찍는다(`src-tauri/src/util.rs`) — 클라이언트가 이보다
   낮은 정밀도(초 단위 등)를 쓰면 같은 초 안의 연속 갱신이 동률로 뭉개져 LWW 비교가 어긋난다.
3. 삭제는 **tombstone 으로 전파**한다 — 클라이언트가 로컬에서 뭔가를 지웠다고 서버 쪽 행이
   조용히 남으면 "삭제가 부활하는 버그"가 된다(`docs/SYNC.md` §6). 서버 쪽 tombstone 테이블은
   이미 있다: `deleted_rows(tbl, id, deleted_at)`(V24, `repo/tombstone.rs`).
4. 모든 쓰기에 **`device_id`** 를 남긴다 — 충돌 판정과 디버깅의 기본 축(`docs/SYNC.md` G3).
   `device_id` 는 설치본 식별자이지 사용자 데이터가 아니다 — 번들/백업에 담아 다른 기기로
   옮기지 않는다(§6 참고, `repo/transfer/export.rs::is_device_local_setting_key`,
   `repo/transfer/backup.rs`의 복원 시 재생성 로직과 동일한 원칙).
5. **부분 동기화 금지 — 노트 단위 원자성.** 노트 하나를 쓸 때는 note 본체 + sections +
   attachments + tags를 **함께** 커밋한다. section만 도착하고 note가 아직 없는 상태, 또는 그
   반대가 다른 클라이언트에 노출되면 안 된다. 데스크톱 repo 계층이 이미 이 형태다(트랜잭션 단위
   쓰기) — 원격 쓰기 API가 생기면 같은 원자성을 API 레벨에서 지켜야 한다.
6. **시계 오차 안전장치(로드맵, 미구현).** LWW는 기기 시계에 의존하므로, 양방향 동기화를
   구현할 때 핸드셰이크에서 서로의 현재 시각을 교환해 오차가 임계값(예: 2분) 이상이면
   동기화를 진행하되 사용자에게 경고를 표시한다(2026-07-29 owner 논의). 자동 보정은 하지
   않는다 — 시계를 고치는 것은 사용자 몫이고, 앱이 몰래 timestamp를 조작하면 디버깅 불능이 된다.

**현재 구현**
- 배포된 쓰기 엔드포인트: `POST /api/v1/invoke`(노트 생성/수정 포함 — `http:true` 커맨드
  브리지, `note_create`/`note_update`/`section_update`/`note_get` 등),
  `POST /api/v1/notes/{note_id}/checklist`(체크박스 토글),
  `POST /api/v1/notes/{note_id}/attachments`(첨부 업로드) — 요청/응답 셰이프는
  `specs/commands/sync.yaml` `http_write_api`. 예전 `POST /api/v1/notes` ·
  `PUT /api/v1/notes/{id}` · `GET /api/v1/notes/{id}` REST CRUD는 클라이언트가 없어 삭제됐다.
- 규칙 1~3(LWW/밀리초 정밀도/tombstone)은 이미 만족한다 — invoke 가 데스크톱과 같은 커맨드
  함수를 타고, checklist/attachments REST는 `repo::sections::update`/`repo::attachments::add_file`
  을 재사용하므로 `updated_at` 전파와 tombstone 기록이 자동으로 따라온다(재구현이 아니라
  재사용이라 이 두 규칙은 어길 방법 자체가 없다).
  > **갭 — 규칙 4(device_id)는 현재 구현이 만족하지 못한다.** 위 쓰기 경로 중 어느 것도
  > 어느 기기가 그 쓰기를 했는지 기록하지 않는다 — desktop repo 함수들 자체가 `device_id`
  > 파라미터를 받지 않는다(오늘은 "단일 소유자, 최대 두 기기"라 이 정보가 없어도 실사용에
  > 문제가 없다 — 위 preamble 참고). 양방향 동기화(여러 기기가 실제로 충돌할 수 있는 상태)
  > 전에 채워야 한다.
  > **갭 — 규칙 5(노트 단위 원자성)는 부분적으로만 만족한다.** 노트 본문 쓰기는
  > `POST /api/v1/invoke`의 `note_update`/`section_update`로 가며, desktop 에디터와 같이
  > title 1건 + section마다 1건의 독립 트랜잭션이다. 두 번째 section 갱신이 실패하면 첫 번째
  > section 은 이미 커밋된 채로 남는다 — "노트 전체가 한 요청 안에서 원자적"이라는 규칙 5의
  > 문구를 문자 그대로는 만족하지 못한다. 실사용 영향은 작다(각 section 갱신 자체는 독립적으로
  > 유효한 상태이고, 실패한 section 하나만 재시도하면 됨) — 그러나 "부분 동기화 금지"라는
  > 규칙 이름과는 어긋나므로 갭으로 명시해 둔다.
  > **갭 — 규칙 6(시계 오차)은 규칙 자체가 "로드맵, 미구현"으로 이미 표시돼 있다** — 현재 쓰기
  > 엔드포인트들은 서버(데스크톱) 시계만 신뢰하고 클라이언트(모바일 브라우저) 시계는 아예 보지
  > 않는다(요청에 타임스탬프가 실리지 않고, `updated_at` 은 서버가 `now_iso()` 로 직접 찍는다) —
  > 그래서 시계 오차 자체가 지금은 관측되지 않는다. 양방향 동기화로 넘어가 클라이언트도
  > 타임스탬프를 갖고 오는 순간부터 규칙 6이 실제로 필요해진다.

## 5. 보안 규칙

**규칙**
1. 서버는 **tailnet 또는 localhost 밖에 바인딩하지 않는다.** 공인 인터넷에 노출되는 바인딩은
   어떤 이유로도 금지 — Tailscale의 CGNAT 대역(`100.64.0.0/10`) 또는 `127.0.0.1`/`localhost`만
   허용한다.
2. **`/api/v1/*` 데이터 엔드포인트는 예외 없이 토큰 인증을 요구한다** — `ping`처럼 무해해 보이는
   엔드포인트도 포함한다(존재 여부 자체를 정보 노출로 볼 수 있음). 유일한 예외는 웹 클라이언트의
   **정적 번들(`/app`) 자체**다 — 브라우저가 앱을 띄우려면 그 번들(HTML/JS/CSS)은 먼저 받아야
   하므로 번들 응답은 인증 없이 서빙할 수 있다. 단 그 번들은 토큰이 확인되기 전까지 **노트
   데이터를 단 한 바이트도 포함하거나 불러오지 않아야 한다** — 데이터는 전부 `/api/v1/*` 호출로만
   오고, 그 호출은 규칙 그대로 토큰을 요구한다. (구형 `/m`, 루트 `/`는 이제 셸이 아니라 쿼리스트링
   보존 307 리다이렉트일 뿐이다 — 리다이렉트 자체도 인증 없이 통과하지만 데이터를 담지 않는다.)
3. TLS는 이 서버가 직접 구현하지 않는다 — **Tailscale 계층이 담당**한다(tailnet 트래픽은 이미
   WireGuard로 암호화됨). 평문 TCP를 공인망에 노출하지 않는 한 이 전제가 유지된다(규칙 1과 결합).
4. 토큰은 **설정 화면에서 재발급 가능**해야 한다 — 유출 의심 시 즉시 무효화할 방법이 항상 있어야
   한다.
5. **기본 상태는 서버 꺼짐(opt-in)이다.** 사용자가 명시적으로 켜기 전까지 앱은 어떤 포트도 열지
   않는다 — 로컬 우선(local-first) 정체성과 "설치만 해도 뭔가가 네트워크에 열려 있다"는 불안을
   피한다.

**현재 구현(목표)**
- 설정 키: `sync_enabled`(bool, 기본 false), `sync_port`(기본 7332), `sync_token`(재발급 가능).
  바인딩 주소는 Tailscale CGNAT 대역 우선, 실패 시 localhost 폴백.

## 6. 공유/이식 규칙 (장기 안정성)

이 절은 오늘(2026-07-29) 확정된 방향이며, export/import/백업 인프라가 이미 부분적으로 이 원칙
위에 있다.

**규칙**
1. **태그는 import 시 이름 기준으로 병합한다** — 동일한 노트북에 동명 태그가 중복 생성되면
   안 되고, 병합 결과 노트가 태그를 잃어서도 안 된다. 서로 다른 기기에서 독립적으로 만든 같은
   이름의 태그가 서로 다른 UUID를 갖는 것은 당연하므로(전역 랜덤 ID, 아래 3), ID만 비교하면
   "새 태그"로 오인하거나 연결을 놓친다.
   > **갭 — 현재 구현은 이 규칙을 만족하지 못한다(중복이 아니라 조용한 유실).**
   > `specs/db/schemas/notes.sql`의 `tags.name` 은 `COLLATE NOCASE UNIQUE` 라 동명 태그 자체는
   > 중복 생성되지 않는다 — 그러나 `repo/transfer/import.rs::import_bundle` 의
   > `INSERT OR IGNORE INTO tags(id, name)` 이 이름 충돌로 스킵되면, 번들이 들고 온 `tag_id`
   > 는 로컬에 존재하지 않는 채로 남는다. 뒤이은
   > `INSERT OR IGNORE INTO note_tags(note_id, tag_id)` 는 그 존재하지 않는 `tag_id` 를 참조하며
   > `foreign_keys=ON`(`db::mod.rs` 부트스트랩) 상태에서 FK 위반으로 **조용히 스킵**된다 — 이
   > 조용한-스킵 자체는 이 파일이 `workspace_regions`/`workspace_eras` 삽입에서 이미 의도적으로
   > 쓰는 패턴("대상 노트북이 번들에 없으면 FK 위반으로 조용히 skip")과 같은 메커니즘이다.
   > 결과: 동명 태그를 가진 다른 기기의 번들을 merge-import 하면, 그 노트는 로컬에 이미 있는
   > (다른 id의) 동명 태그로 재연결되는 대신 **태그 연결 자체가 조용히 사라진다.** §8 원칙("코드가
   > 규칙과 어긋나면 코드가 버그")에 따라 알려진 결함이며, 교정 방향은 태그 삽입 전에 이름으로
   > 기존 태그를 조회해 있으면 그 id를 재사용하고 없을 때만 번들의 id로 새로 만드는 것이다
   > (`note_tags` 는 항상 실제 로컬 tag id를 참조).
2. 번들에 **provenance(출처) 필드는 예약**한다 — `Bundle`(`repo/transfer/export.rs`)에
   `source_device_id`(출처 device의 id), `source_workspace_id`(출처 workspace의 id) 두 필드
   이름을 지금 확정하되, **구현(채우기/읽기)은 하지 않는다.** 지금 채우면 §1 YAGNI 위반이고,
   이름만 지금 고정해두면 나중에 실제 provenance 추적이 필요해졌을 때 이미 배포된 구버전 번들
   (필드 없음)과의 하위호환을 §2 optional-field 규칙으로 그대로 흡수할 수 있다 — 그 시점에 다른
   이름을 새로 짓지 않는다.
3. **ID는 전역 랜덤(UUIDv4)이라 타인의 번들을 병합해도 안전**하다 — 자동 증가 정수 PK였다면
   기기 간 ID 충돌이 발생했겠지만(`docs/SYNC.md` §1 "이미 갖춘 것"), UUID라 어떤 두 기기의
   번들을 섞어도 ID 공간이 겹치지 않는다.
4. **merge는 기존 ID를 skip하는 멱등 연산이다** — 같은 번들을 두 번 merge-import해도 두 번째는
   전부 스킵되어 결과가 달라지지 않는다. `repo/transfer/import.rs`의 `mode="merge"` 는 이미 이
   형태다(`SELECT 1 FROM notes WHERE id=?1` 존재 확인 후 skip). 새로 생기는 어떤 이식 경로도
   이 멱등성을 깨서는 안 된다 — 재시도가 안전해야 네트워크 실패 시 "다시 보내기"가 데이터를
   중복시키지 않는다.

**규칙**
